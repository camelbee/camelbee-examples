3-layer route architecture: **Consumer → Central → Producer**

| Layer | Location | Role |
|-------|----------|------|
| Consumer | `routes/consumer/{technology}/` | Entry points — unmarshal, validate, map API→Domain |
| Central | `routes/central/` | Orchestration — fan-out to backends |
| Producer | `routes/producer/{technology}/` | Outgoing — map Domain→Infra, call backend |

**Models:** `model/api/` (API) → `model/domain/` (internal) → `model/infra/` (backend)
**Mappers:** `mapper/api/` (API↔Domain), `mapper/infra/` (Domain↔Infra) — MapStruct

**MUST preserve** (breaking these breaks CamelBee observability):
- `camelBeeRouteConfigurer.configureRoute(this)` — first call in every route's `configure()`
- `errorHandler(genericExceptionHandler.appErrorHandler())` — consumer routes only
- `errorHandler(noErrorHandler())` — central and producer routes
- Exchange properties: `Constants.ORIGINAL_BODY`, `Constants.ACTUAL_RESPONSE_BODY`, `Constants.ORIGINAL_ACCEPT_CONTENT_TYPE`
- `.routeId()` on every route, `.id()` on every backend endpoint in central routes
- 3-layer flow: Consumer → Central → Producer (never call backend from consumer directly)
- **`toString()` on hand-written model classes:** Any object set as the exchange body that flows between routes MUST have a meaningful `toString()` method. The CamelBee tracer and debugger UI call `toString()` to collect and display message bodies, and logging also relies on it for tracing. Without a proper `toString()`, messages appear as unreadable object references in the UI and logs. Models generated by Maven plugins (OpenAPI, Protobuf, Avro, JAXB, etc.) already have proper `toString()` from their generators. But any model class you create manually under `src/main/java` (domain objects, DTOs, event wrappers, etc.) must include it — use Lombok `@ToString` or implement it manually. This does NOT apply to `String` or streaming types which are already readable.

**Do NOT:**
- Change dependency/plugin versions unless explicitly asked
- Modify TestContainers, Docker Compose, or test infrastructure unless broken by your change
- Add workarounds for "compatibility issues" — the generated code works as-is
- Restructure the project layout or build configuration
- Skip success scenarios in tests — every new feature MUST have both success AND error tests

**Testing requirements (MANDATORY):** Every new operation or feature must include:
- **Unit tests:** at least 1 success + 1 error scenario (AdviceWith mocks)
- **Integration tests:** at least 1 success scenario with real backend data verification + 1 error scenario. Do NOT only write error tests — set up the backend test data (DB records, WireMock stubs, queue messages) needed for success scenarios
- **Black-box tests:** at least 1 success scenario with backend data verification + 1 error scenario. Do NOT skip success tests because backend setup is complex — study existing tests for how to set up test data

**Running tests:** After implementing code and tests, ask the developer if they want you to run the tests. If yes, run them yourself — do not ask the developer to run them manually. Run in order: unit tests first (`./mvnw test`), then integration tests (`./mvnw jacoco:prepare-agent failsafe:integration-test failsafe:verify`), then black-box tests (`./mvnw verify -Pblack-box-test`). If any test fails, fix the issue and re-run.

**If something breaks after your change**, fix your change — don't blame the infrastructure.


| Rule | Wrong | Right |
|---|---|---|
| JSON marshal | `.marshal().json()` | `.marshal(jacksonDataFormat)` with injected `ObjectMapper` |
| JSON unmarshal | `.unmarshal().json(JsonLibrary.Jackson, X.class)` | `.unmarshal(xFormat)` with `JacksonDataFormat` |
| MapStruct | `componentModel = "spring"` | `componentModel = "cdi"` |
| DI | `@Component` | `@ApplicationScoped` |
| Split expr | Lambda in `.split()` | `method(this, "methodName")` (native) |
| Collection DI | `List<T>` | `Instance<T>` |
