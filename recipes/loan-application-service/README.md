## Overview

This microservice was generated by [CamelBee](https://camelbee.io) using Apache Camel and Springboot.
It acts as a **scalable integration layer** designed to bridge multiple protocols and backends.

**Key Features:**

### Interfaces (Consumers)
- **REST API** with OpenAPI/Swagger support
- **Kafka Consumer** for event-driven processing
- **MCP Tools** for AI agent integration (Model Context Protocol)

### Backends (Producers)
- **REST Backend** for external API integration
- **Kafka Producer** for event publishing
- **JPA Backend** with Hibernate ORM
- **Cache Backend** for caching layer

### Additional Features
- **Apache Avro** support
- **CamelBee Observability** — Built-in route topology UI, debugger, and metrics
- **MapStruct Mapping** — Type-safe object transformations
- **Native Executable** support (GraalVM)
- **Production-Ready** — Health checks, Prometheus metrics, Docker, Kubernetes

## Dependency Management

This microservice inherits from the [CamelBee parent POM](https://github.com/camelbee/camelbee/blob/main/parent/pom.xml) which provides centralized dependency management. All dependency versions are pre-configured, tested, and maintained by CamelBee — no manual version alignment required.

**Benefits:**

- **Zero version conflicts** — All dependencies are tested together for compatibility
- **Simplified pom.xml** — No need to specify versions for common dependencies
- **Easy upgrades** — Update the parent version to get all dependency updates
- **Framework-specific BOMs** — Optimized for Quarkus or Spring Boot

**Dependency Hierarchy:**
```
camelbee/
├── parent/pom.xml                    # Build plugins, quality tools, common config
├── dependencies/pom.xml              # Shared dependencies across frameworks
└── dependencies/springboot/pom.xml   # Spring Boot-specific dependencies & BOM
```

| Module | Purpose | Source |
|--------|---------|--------|
| **Parent POM** | Build plugins, quality tools, compiler settings | [parent/pom.xml](https://github.com/camelbee/camelbee/blob/main/parent/pom.xml) |
| **Dependencies** | Common dependencies shared across frameworks | [dependencies/pom.xml](https://github.com/camelbee/camelbee/blob/main/dependencies/pom.xml) |
| **Spring Boot Dependencies** | Spring Boot BOM, Camel Spring Boot starters | [dependencies/springboot/pom.xml](https://github.com/camelbee/camelbee/blob/main/dependencies/springboot/pom.xml) |

## Quick Start

### Prerequisites

- Java 21+
- Maven 3.9+ (or use the included Maven wrapper)
- Docker (optional, for running dependencies)
- GraalVM (optional, for native builds)

### Run

**1. Start backend dependencies**

For local development, start the required backend services:

```bash
docker compose -f src/integration-test/resources/compose-backends.yml up -d
```

**2. Start the application**

```bash
chmod +x mvnw    # first time only
./mvnw spring-boot:run
```

> **Application:** http://localhost:8080

**Route Visualization with CamelBee UI**

The CamelBee React UI is embedded in the microservice and available at:

> **CamelBee UI:** http://localhost:8080/camelbee/index.html

1. Start your microservice locally
2. Open http://localhost:8080/camelbee/index.html in your browser
3. Click **Debugger** to trace message flows or **Metrics** to view route performance statistics

**Backend Services (src/integration-test/resources/compose-backends.yml)**

The `compose-backends.yml` provides all required infrastructure for local development:

| Service | Port | Purpose |
|---------|------|---------|
| WireMock | 8091 | Mock backend services |
| PostgreSQL | 5432 | Database |
| Kafka | 9092 | Event streaming |
| Zookeeper | 2181 | Kafka coordination |

> **Note:** For integration tests, TestContainers automatically manages these services. Manual startup is only needed for local development.

**Stop backends when done**

```bash
docker compose -f src/integration-test/resources/compose-backends.yml down
```

### Verify

```bash
curl http://localhost:8080/health
```

## CamelBee Observability

This microservice comes with built-in observability features provided by [CamelBee](https://camelbee.io). All backend calls are automatically logged and traced without requiring additional logging statements in your code.

**Automatic Configuration:**

Every route is automatically configured with error handling and observability:
```java
@Override
public void configure() throws Exception {
    camelBeeRouteConfigurer.configureRoute(this);            // Enables tracing, MDC logging, stream caching
    errorHandler(genericExceptionHandler.appErrorHandler()); // Global error handling
    
    // Your route definition...
}
```

**Features:**

| Feature | Description | Source |
|---------|-------------|--------|
| **Event Notifier** | Automatically captures exchange events (created, completed, failed) across all routes | [CamelBeeEventNotifierConfigurer](https://github.com/camelbee/camelbee/blob/main/core/quarkus-core/src/main/java/org/camelbee/config/CamelBeeEventNotifierConfigurer.java) |
| **Route Configurer** | Configures stream caching, MDC logging, and CamelBeeUnitOfWork for all routes | [CamelBeeRouteConfigurer](https://github.com/camelbee/camelbee/blob/main/core/quarkus-core/src/main/java/org/camelbee/config/CamelBeeRouteConfigurer.java) |
| **Tracer** | Intercepts and caches request/response messages for all Camel components | |
| **Global Error Handler** | Centralized exception handling with consistent error responses | |

**Configuration (`application.yaml`):**
```yaml
camelbee:
  # Registers CamelBee event notifier to the Camel context
  notifier-enabled: true
  
  # Configures stream caching, MDC logging and CamelBeeUnitOfWork for routes
  route-configurer-enabled: true
  
  # Allows CamelBee UI to fetch the Camel Context topology
  context-enabled: true
  
  # Intercepts/traces request and responses of all camel components
  tracer-enabled: true
  
  # Maximum idle time before deactivating message tracing (ms)
  tracer-max-idle-time: 60000
  
  # Maximum number of traced messages to cache
  tracer-max-messages-count: 10000
  
  # Logs messages exchanged between endpoints
  logging-enabled: true
```

**What Gets Logged Automatically:**

- All incoming requests (REST, gRPC, GraphQL, SOAP, messaging, etc.)
- All outgoing backend calls (REST, database, messaging, etc.)
- Exchange metadata (headers, properties, timestamps)
- Error details with full stack traces
- Route execution flow and timing

**Visualize with CamelBee UI:**

When `tracer-enabled: true`, you can visualize live message flows at the built-in CamelBee UI:

1. Start your microservice locally
2. Open http://localhost:8080/camelbee/index.html
3. Click **Debugger** to trace message flows in real-time
4. Click **Metrics** to view route performance statistics

> **Tip:** For production, consider setting `tracer-enabled: false` and `logging-enabled: false` to reduce overhead, while keeping `notifier-enabled: true` for metrics collection.

**Disabling Observability:**

To disable specific features, update `application.yaml`:
```yaml
camelbee:
  notifier-enabled: false      # Disable event notifications
  tracer-enabled: false        # Disable message tracing
  logging-enabled: false       # Disable automatic logging
```

| `/cb-add-backend <TECH>` | Scaffold a new producer backend via the CamelBee MCP server |
| `/cb-add-operation <name>` | Add a new operation beyond the default CRUD set (CRO, LSO, GEO, REO, UPO, DEO, CRB) |
| `/cb-replace-domain <Singular> <Plural>` | Guided walkthrough to swap the Order/Purchase reference domain for your own |
| `/cb-regen` | Regenerate spec-driven Java code (`./mvnw generate-sources`) after editing any spec |
| `/cb-run-tests [level]` | Run unit, integration, black-box, or load tests |
| `/cb-coverage [level]` | Generate + display JaCoCo coverage report |
| `/cb-review [file]` | Review code for CamelBee anti-patterns and missing tests |
| `/cb-debug [interface]` | Trigger a request and verify flow in the CamelBee debugger UI |
| `/cb-load-test [protocol]` | Run k6 load tests from `docs/k6/` against the running service |
| `/cb-add-migration <description>` | Add a new Flyway migration across every active DB vendor directory |

### Path-scoped rules (loaded automatically when you edit matching files)

These load silently when the AI reads or edits a matching file — you don't invoke them. They bring CamelBee-specific conventions into the AI's context:

- **`route-architecture`** — 3-layer architecture, model tiers, error handling, protocol patterns
- **`camel-dsl-patterns`** — Camel DSL code examples per technology, marshaling, content negotiation
- **`test-patterns`** — Unit/integration/black-box test patterns, credential alignment matrix
- **`build-plugins`** — Maven code generation pipeline
- **`observability-patterns`** — CamelBee tracer, debugger UI, MDC correlation, logging, error framework
- **`security-patterns`** — OAuth2/JWT, Keycloak, JWKS caching, role/scope checks
- **`db-migration-patterns`** — Flyway migrations, per-vendor quirks, DataSeeder reset scripts

### Claude Code subagents

- **`code-reviewer`** — independent code review using a different model for perspective
- **`test-writer`** — fills missing tests (unit + integration + black-box) for existing code, following the project's existing patterns

Invoked automatically by the main AI when it decides to delegate, or explicitly: "use the test-writer agent to cover this route."

### Filtering AI files

Generated with `-DaiTools=all`. Re-generate with a different value to change the mix — accepted: `all`, `none`, or any comma-separated subset of `claude,cursor,codex,opencode,copilot`.

## Cache Backend Reference

Write-through cache backend — keeps the cache in sync with primary-backend writes.

**Route:** `src/main/java/io/fintech/loan/application/service/routes/producer/cache/CacheProducerRoute.java`

### Vendor

**Redis** (`camel-spring-redis`) — host/port via `camelbeeservice.cache.host` / `camelbeeservice.cache.port`.

### Value Format

JSON only. The `Purchase` infra model is serialized to JSON before being stored.

### Cache Key

`camelbeeservice:purchase:{id}`

### Supported Operations

Write-through only — no `listOrders` (LSO) or `getOrder` (GEO). Read-through / cache-aside patterns require conditional routing, not fan-out.

| Operation | Action |
|-----------|--------|
| Create (CRO) | PUT/SET `camelbeeservice:purchase:{id}` |
| Update (UPO) | PUT/SET `camelbeeservice:purchase:{id}` |

## Logging

This microservice uses Spring Boot logging with Logback. JSON format is automatically enabled for production environments, while plain text is used for development and testing.

**Configuration Files:**

| File | Purpose |
|------|---------|
| `src/main/resources/application.yml` | Log levels per profile |
| `src/main/resources/logback-spring.xml` | Log format, appenders, MDC fields |

**Log Levels:**

Default log levels are configured in `logback-spring.xml`:
```xml
<logger name="io.camelbee" level="INFO"/>
<logger name="org.apache.camel.component.http" level="INFO"/>
<logger name="org.apache.camel" level="INFO"/>

<root level="INFO">
    <appender-ref ref="STDOUT"/>
</root>
```

Profile-specific overrides in `application.yml`:
```yaml
# Test profile
---
spring:
  config:
    activate:
      on-profile: test

logging:
  level:
    root: DEBUG
    io.camelbee: DEBUG

---
# Integration test profile
spring:
  config:
    activate:
      on-profile: itest

logging:
  level:
    root: DEBUG
    io.camelbee: DEBUG
    org.apache.camel: DEBUG

---
# Production profile
spring:
  config:
    activate:
      on-profile: prod

logging:
  level:
    root: INFO
    io.camelbee: INFO
```

**Log Format by Profile:**

| Profile | Format | Use Case |
|---------|--------|----------|
| `dev`, `test`, `itest` | Plain text | Local development, debugging |
| `prod` | JSON (Logstash) | Production, log aggregation (ELK/Splunk) |

**Plain Text Format (dev/test/itest):**
```
2024-01-15 10:30:45.123 INFO  [main] c.m.r.c.r.RestConsumerRoute - Processing order ORD-001
```

Pattern: `%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] %logger{36} - %msg%n`

**JSON Format (prod):**
```json
{
  "@timestamp": "2024-01-15T10:30:45.123+0000",
  "level": "INFO",
  "logger_name": "com.mycompany.routes.consumer.rest.RestConsumerRoute",
  "message": "Processing order ORD-001",
  "app": "camelbee",
  "environment": "production",
  "tx_request_uri": "/api/orders",
  "tx_request_body": "{...}",
  "businessTransactionId": "abc-123-def"
}
```

**MDC Context (Automatic):**

CamelBee automatically adds MDC fields to all log entries when `route-configurer-enabled: true`:

| MDC Field | Description |
|-----------|-------------|
| `tx_request_uri` | Request URI |
| `tx_request_body` | Request body |
| `tx_request_headers` | Request headers |
| `tx_response_body` | Response body |
| `tx_response_headers` | Response headers |
| `businessTransactionId` | Business transaction correlation ID |
| `log_type` | Log entry type |

MDC logging is enabled in `application.yml`:
```yaml
camel:
  springboot:
    use-breadcrumb: true
    use-m-d-c-logging: true
```

**Changing Log Levels:**

Via command line:
```bash
java -jar target/loan-application-service-0.0.1-SNAPSHOT.jar --logging.level.root=DEBUG
```

Via environment variable:
```bash
LOGGING_LEVEL_ROOT=DEBUG java -jar target/loan-application-service-0.0.1-SNAPSHOT.jar
```

Via Spring profile:
```bash
java -jar target/loan-application-service-0.0.1-SNAPSHOT.jar --spring.profiles.active=prod
```

**Customizing Log Format:**

To modify the log format, edit `src/main/resources/logback-spring.xml`:
```xml
<!-- Plain text pattern -->
<encoder>
    <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] %logger{36} - %msg%n</pattern>
</encoder>

<!-- Add custom MDC fields for JSON -->
<includeMdcKeyName>myCustomField</includeMdcKeyName>

<!-- Add custom static fields for JSON -->
<customFields>{"app":"myapp","team":"myteam"}</customFields>
```

> **Tip:** For production deployments with ELK/Splunk/CloudWatch, the JSON format with `@timestamp` field and flat MDC fields is optimized for log aggregation and searching.

### Black-Box Tests

Black-box tests validate the fully **dockerized** application end-to-end. Unlike integration tests which embed the application, black-box tests build a Docker image from the application and test it externally via HTTP using RestAssured.

**Prerequisites:**
- Docker must be running
- The application must be packaged first (the Docker image is built from `target/`)

```bash
# Step 1: Build the application jar
./mvnw package -DskipTests

# Step 2: Run black-box tests (TestContainers builds the Docker image and starts all services)
./mvnw verify -Pblack-box-test
```

> **Note:** The black-box test profile uses TestContainers to:
> - Build the application Docker image from `src/main/docker/Dockerfile.jvm`
> - Start all backend services from `compose-backends.yml`
> - Wait for the application health endpoint to be ready
> - Run tests against the dockerized application
> - Stop and clean up all containers

**Memory Tuning:**

The Docker Compose files (`compose-blackbox.yml`, `docker-compose.yml`) include JVM memory settings via `JAVA_OPTS`. If your microservice has many interfaces and backends, you may need to increase these values:

| Setting | Default | Many Technologies |
|---|---|---|
| `MetaspaceSize` | 512m | Increase if OOM Metaspace errors |
| `MaxMetaspaceSize` | 1024m | Increase if OOM Metaspace errors |
| Container `memory` limit | 4G | Increase if needed |

Adjust these in the `environment` and `deploy.resources` sections of the compose files.

### Quality Checks

This project inherits from the [CamelBee parent POM](https://github.com/camelbee/camelbee/blob/main/parent/pom.xml) which includes pre-configured static code analysis tools.

**Configuration Inheritance:**

The quality tool configurations are centralized in the [io.camelbee:common](https://github.com/camelbee/camelbee/tree/main/common) module:
```
common/
├── config/
│   ├── checkstyle/
│   │   └── google-checks.xml           # Google Java Style rules
│   └── spotbugs/
│       └── exclude.xml                 # SpotBugs exclusion patterns
└── formatter/
    ├── eclipse-java-google-style.xml   # Eclipse formatter config
    └── intellij-java-google-style.xml  # IntelliJ formatter config
```

These configurations are automatically unpacked to `target/` during the build's `validate` phase, ensuring consistent code style across all CamelBee-generated microservices.

**Code Formatting:**

The project uses the [formatter-maven-plugin](https://code.revelc.net/formatter-maven-plugin/) with Google Java Style. Code is automatically formatted during the `validate` phase of every build.
```bash
# Manually format code
./mvnw formatter:format

# Validate formatting without changes
./mvnw formatter:validate
```

**Disabling Formatting for Specific Code Blocks:**

To prevent formatting on specific code sections (e.g., complex SQL strings, DSL builders), use formatter tags:
```java
// @formatter:off
String sql = "SELECT id, name, status " +
             "FROM   orders " +
             "WHERE  status = 'ACTIVE' " +
             "ORDER  BY created_at DESC";
// @formatter:on
```

> **Tip:** The `// @formatter:off` and `// @formatter:on` comments are recognized by both the Maven plugin and most IDEs (IntelliJ, Eclipse, VS Code).

**Available Tools:**

| Tool | Purpose | Official Site |
|------|---------|---------------|
| **Formatter** | Automatically formats Java code according to Google Java Style during build. Ensures consistent code formatting across the team. | [code.revelc.net/formatter-maven-plugin](https://code.revelc.net/formatter-maven-plugin/) |
| **Checkstyle** | Enforces coding style and conventions. Ensures developers write Java code that adheres to a defined coding standard (Google Checks), checking for formatting, naming conventions, and code structure. | [checkstyle.org](https://checkstyle.org/) |
| **PMD** | Detects common programming flaws such as unused variables, empty catch blocks, unnecessary object creation, and copy-paste code (CPD). Works at the source code level. | [pmd.github.io](https://pmd.github.io/) |
| **SpotBugs** | Finds potential bugs in compiled Java bytecode using static analysis. Detects null pointer dereferences, infinite loops, resource leaks, and security vulnerabilities. Successor of FindBugs. | [spotbugs.github.io](https://spotbugs.github.io/) |
| **SonarQube** | Continuous code quality and security analysis platform. Provides a centralized dashboard for tracking code smells, bugs, vulnerabilities, technical debt, and test coverage across projects. | [sonarqube.org](https://www.sonarqube.org/) |

**Run quality checks (local):**

**Customizing Quality Rules:**

To override the default configurations, create your own config files in your project:
```
loan-application-service/
├── config/
│   ├── checkstyle/
│   │   └── checkstyle.xml              # Your custom Checkstyle rules
│   ├── spotbugs/
│   │   └── exclude.xml                 # Your custom SpotBugs exclusions
│   ├── pmd/
│   │   └── ruleset.xml                 # Your custom PMD rules
│   └── formatter/
│       └── eclipse-formatter.xml       # Your custom formatter config
└── pom.xml
```

Then add the following to your project's `pom.xml` to override the default configurations:
```xml
<build>
  <plugins>

    <!-- Override Formatter config -->
    <plugin>
      <groupId>net.revelc.code.formatter</groupId>
      <artifactId>formatter-maven-plugin</artifactId>
      <configuration>
        <configFile>${project.basedir}/config/formatter/eclipse-formatter.xml</configFile>
      </configuration>
    </plugin>

  </plugins>
</build>

<profiles>
  <profile>
    <id>quality</id>
    <build>
      <plugins>
        
        <!-- Override Checkstyle config -->
        <plugin>
          <groupId>org.apache.maven.plugins</groupId>
          <artifactId>maven-checkstyle-plugin</artifactId>
          <configuration>
            <configLocation>${project.basedir}/config/checkstyle/checkstyle.xml</configLocation>
          </configuration>
        </plugin>

        <!-- Override SpotBugs exclusions -->
        <plugin>
          <groupId>com.github.spotbugs</groupId>
          <artifactId>spotbugs-maven-plugin</artifactId>
          <configuration>
            <excludeFilterFile>${project.basedir}/config/spotbugs/exclude.xml</excludeFilterFile>
          </configuration>
        </plugin>

        <!-- Override PMD rules -->
        <plugin>
          <groupId>org.apache.maven.plugins</groupId>
          <artifactId>maven-pmd-plugin</artifactId>
          <configuration>
            <rulesets>
              <ruleset>${project.basedir}/config/pmd/ruleset.xml</ruleset>
            </rulesets>
          </configuration>
        </plugin>

      </plugins>
    </build>
  </profile>
</profiles>
```

> **Note:** The formatter plugin override goes in the main `<build>` section (runs during `validate` phase), while Checkstyle, PMD, and SpotBugs overrides go inside the `quality` profile.

> **Tip:** You can export formatter settings from your IDE:
> - **Eclipse:** Preferences → Java → Code Style → Formatter → Export
> - **IntelliJ:** Settings → Editor → Code Style → Java → Export (select "Eclipse XML Profile")

**Suppressing Rules Inline:**

You can also suppress specific rules directly in your code using annotations or comments:

| Tool | Suppression Method |
|------|-------------------|
| Formatter | `// @formatter:off` ... `// @formatter:on` |
| Checkstyle | `@SuppressWarnings("checkstyle:MagicNumber")` |
| SpotBugs | `@SuppressFBWarnings("NP_NULL_ON_SOME_PATH")` |
| PMD | `@SuppressWarnings("PMD.UnusedLocalVariable")` |
