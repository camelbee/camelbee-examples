**MUST preserve** (breaking these breaks CamelBee observability):
- `camelBeeRouteConfigurer.configureRoute(this)` — first call in every route's `configure()`
- `errorHandler(genericExceptionHandler.appErrorHandler())` — consumer routes only
- `errorHandler(noErrorHandler())` — central and producer routes
- Exchange properties: `Constants.ORIGINAL_BODY`, `Constants.ACTUAL_RESPONSE_BODY`, `Constants.ORIGINAL_ACCEPT_CONTENT_TYPE`
- `.routeId()` on every route, `.id()` on every backend endpoint in central routes
- 3-layer flow: Consumer → Central → Producer (never call backend from consumer directly)
- **Contract-first REST binding:** `rest().openApi().specification("openapi/<your-api>.yaml").missingOperation("ignore")` in the REST consumer route. REST endpoints are created FROM the OpenAPI spec — each `operationId` becomes a `from("direct:{operationId}")` route. Everything about the spec is yours to change: rename the file (update the path here AND in the pom.xml `<inputSpec>`), rename schemas, paths, and operationIds, then run `./mvnw generate-sources` and rename the `direct:` routes to match. What must NOT change is the mechanism: never delete the `rest().openApi()` binding and hand-define endpoints with `rest().get(...)` / `rest().post(...)` verbs in Java — that silently detaches the API from the spec that the generated models, Postman collection, and test clients are all derived from
- **`@ToString` on ALL model classes (api / domain / infra):** The CamelBee tracer and debugger UI call `toString()` on every exchange body to display message content. Without a proper `toString()`, every message in the UI and in logs appears as `ClassName@abc123` — completely unreadable. This applies to all three model layers:
  - `model/api/` — API-facing models (JSON/XML POJOs, event wrappers, CSV records)
  - `model/domain/` — core domain objects (`Order`, `OrderItem`, `Error`, event types)
  - `model/infra/` — backend-specific models (`Purchase`, `PurchaseItem`, etc. for every backend)

  **Generated templates already include `@ToString`.** If you add a new model class manually, always include it — use Lombok `@ToString` as the first choice. For JPA entities with bidirectional relationships, use `@ToString(exclude = "fieldName")` to avoid infinite recursion: exclude the `@ManyToOne` back-reference from `PurchaseItem` (`exclude = "purchase"`) and optionally exclude the `@OneToMany` collection from `Purchase` (`exclude = "items"`). Models code-generated by Maven plugins (OpenAPI Generator, Protobuf, Avro, JAXB) already have `toString()` from their generators — no action needed for those. This rule does NOT apply to `String`, `byte[]`, or streaming types.

**Backend credential / connection alignment (MANDATORY):** Every backend has the **same credential repeated in 3–4 places**. If you change a username, password, host, port, database name, keyspace, collection, topic, queue, bucket, table, or cache name in one place, you MUST update every other place it appears — mismatches surface as `authentication failed`, `Unable to retrieve password for "X"`, `connection refused`, `unknown host`, or silent test failures where `expectedMessageCount(0)` is never violated.

The four touchpoints for every backend:

1. **Docker server config** — `src/integration-test/resources/compose-backends.yml` defines the backend service (env vars like `USER`, `PASS`, `MONGO_INITDB_ROOT_PASSWORD`, `POSTGRES_USER`). This is where the backend container learns what credentials to accept.
2. **App runtime config** — `src/main/resources/application.yml`. The running app reads these when it connects to the backend.
3. **Black-box app env overrides** — `src/black-box-test/resources/compose-blackbox.yml` and `compose-blackbox-native.yml`. When the app runs inside Docker Compose for bbtests, these env vars override `application.yml` (because the app talks to the backend via its Docker service name, e.g. `cache:11222`, not `localhost`).
4. **Test-JVM clients** — `src/black-box-test/java/utils/DataVerifier.java`, `DataSeeder.java`, `MessageVerifier.java`, and integration-test `@BeforeAll` / dynamic route setups. These run in the **Maven JVM on the host**, not inside Docker, so they connect to the **published localhost port** (e.g. `localhost:11222`) with the **same credentials** the server was provisioned with.

When any of the four drifts from the others, tests fail — and often with a message that looks like a bug somewhere else. Example: Infinispan with `USER: camelbee / PASS: camelbee` in `compose-backends.yml` but `username("admin").password("admin")` in `DataVerifier.java` throws `ELY05161: Unable to retrieve password for "admin"` — the server has no `admin` user, the test client was just wrong.

Grep pattern to verify alignment before committing: pick one credential (e.g., `camelbee` for Infinispan, `secret` for Postgres, `example` for MongoDB root) and `grep -rn <credential>` across `src/main/resources`, `src/integration-test/resources`, `src/black-box-test/resources`, and `src/black-box-test/java/utils/`. Every hit must agree.

See `.claude/rules/test-patterns.md` (Claude Code) or `.cursor/rules/test-patterns.mdc` (Cursor) § "Backend credential & connection alignment" for the full matrix per backend.
