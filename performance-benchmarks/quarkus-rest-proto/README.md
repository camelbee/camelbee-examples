## Overview

This microservice was generated by [CamelBee](https://camelbee.io) using Apache Camel and Quarkus.
It acts as a **scalable integration layer** designed to bridge multiple protocols and backends.

**Key Features:**

### Interfaces (Consumers)
- **REST API** with OpenAPI/Swagger support

### Backends (Producers)
- **Mock Backend** for development and testing

### Additional Features
- **Protocol Buffers** support
- **CamelBee Observability** — Route tracer, debugger, and WebGL topology
- **MapStruct Mapping** — Type-safe object transformations
- **Native Executable** support (GraalVM)
- **Production-Ready** — Health checks, Prometheus metrics, Docker, Kubernetes

## CamelBee Observability

This microservice comes with built-in observability features provided by [CamelBee](https://camelbee.io). All backend calls are automatically logged and traced without requiring additional logging statements in your code.

**Automatic Configuration:**

Every route is automatically configured with error handling and observability:
```java
@Override
public void configure() throws Exception {
    camelBeeRouteConfigurer.configureRoute(this);            // Enables tracing, MDC logging, stream caching
    errorHandler(genericExceptionHandler.appErrorHandler()); // Global error handling
    
    // Your route definition...
}
```

**Features:**

| Feature | Description | Source |
|---------|-------------|--------|
| **Event Notifier** | Automatically captures exchange events (created, completed, failed) across all routes | [CamelBeeEventNotifierConfigurer](https://github.com/camelbee/camelbee/blob/main/core/quarkus-core/src/main/java/org/camelbee/config/CamelBeeEventNotifierConfigurer.java) |
| **Route Configurer** | Configures stream caching, MDC logging, and CamelBeeUnitOfWork for all routes | [CamelBeeRouteConfigurer](https://github.com/camelbee/camelbee/blob/main/core/quarkus-core/src/main/java/org/camelbee/config/CamelBeeRouteConfigurer.java) |
| **Tracer** | Intercepts and caches request/response messages for all Camel components | |
| **Global Error Handler** | Centralized exception handling with consistent error responses | |

**Configuration (`application.yaml`):**
```yaml
camelbee:
  # Registers CamelBee event notifier to the Camel context
  notifier-enabled: true
  
  # Configures stream caching, MDC logging and CamelBeeUnitOfWork for routes
  route-configurer-enabled: true
  
  # Allows CamelBee WebGL application to fetch the Camel Context topology
  context-enabled: true
  
  # Intercepts/traces request and responses of all camel components
  tracer-enabled: true
  
  # Maximum idle time before deactivating message tracing (ms)
  tracer-max-idle-time: 60000
  
  # Maximum number of traced messages to cache
  tracer-max-messages-count: 10000
  
  # Logs messages exchanged between endpoints
  logging-enabled: true
```

**What Gets Logged Automatically:**

- All incoming requests (REST, gRPC, GraphQL, SOAP, messaging, etc.)
- All outgoing backend calls (REST, database, messaging, etc.)
- Exchange metadata (headers, properties, timestamps)
- Error details with full stack traces
- Route execution flow and timing

**Visualize with CamelBee WebGL:**

When `tracer-enabled: true`, you can visualize live message flows at [www.camelbee.io](https://www.camelbee.io):

1. Start your microservice locally
2. Visit [www.camelbee.io](https://www.camelbee.io)
3. Enable Local network access in your browser (click the lock icon in the address bar → Permissions → Local network access → Allowed)
4. Connect to `http://localhost:8080`
5. Click **Debugger** to trace message flows in real-time
6. Click **Metrics** to view route performance statistics

> **Tip:** For production, consider setting `tracer-enabled: false` and `logging-enabled: false` to reduce overhead, while keeping `notifier-enabled: true` for metrics collection.

**Disabling Observability:**

To disable specific features, update `application.yaml`:
```yaml
camelbee:
  notifier-enabled: false      # Disable event notifications
  tracer-enabled: false        # Disable message tracing
  logging-enabled: false       # Disable automatic logging
```

## Logging

This microservice uses Quarkus logging with JSON format support for production environments and async logging for performance.

**Log Levels:**

Default log levels are configured in `application.yaml`:
```yaml
quarkus:
  log:
    level: WARN                          # Root log level
    category:
      "io.camelbee":
        level: WARN                      # CamelBee framework logs
      "org.apache.camel":
        level: WARN                      # Apache Camel logs
      "org.apache.camel.component.http":
        level: WARN                      # HTTP component logs
```

**Changing Log Levels:**
```yaml
# For development - more verbose logging
quarkus:
  log:
    level: INFO
    category:
      "com.mycompany":
        level: DEBUG                     # Your application logs
      "org.apache.camel":
        level: INFO
```

Or at runtime via environment variable:
```bash
./mvnw quarkus:dev -Dquarkus.log.level=DEBUG
```

**Async Logging (Performance):**

Async logging is enabled by default to prevent blocking on I/O:
```yaml
quarkus:
  log:
    console:
      async: true                        # Non-blocking log writes
      async-overflow: discard            # Discard logs if queue is full (don't block)
```

**JSON Log Format:**

JSON logging is pre-configured for production/cloud environments:
```yaml
quarkus:
  log:
    json:
      fields:
        timestamp:
          field-name: "@timestamp"       # ELK-compatible timestamp field
        logger-name:
          field-name: "logger_name"
        mdc:
          enabled: true                  # Include MDC context (correlation IDs, etc.)
          flat-fields: true              # Flatten MDC fields at root level
        # Disabled fields for cleaner output
        thread-id:
          enabled: false
        hostname:
          enabled: false
        sequence:
          enabled: false
        process-name:
          enabled: false
        process-id:
          enabled: false
        logger-class-name:
          enabled: false
        thread-name:
          enabled: false
        ndc:
          enabled: false
```

**Sample JSON Log Output:**
```json
{
  "@timestamp": "2024-01-15T10:30:45.123Z",
  "level": "INFO",
  "logger_name": "com.mycompany.routes.consumer.rest.RestConsumerRoute",
  "message": "Processing order ORD-001",
  "camel.breadcrumbId": "abc-123-def",
  "camel.routeId": "rest-create-order",
  "camel.exchangeId": "exchange-456"
}
```

**MDC Context (Automatic):**

CamelBee automatically adds MDC fields to all log entries when `route-configurer-enabled: true`:

| MDC Field | Description |
|-----------|-------------|
| `camel.breadcrumbId` | Unique ID for tracking requests across routes |
| `camel.routeId` | Current route ID |
| `camel.exchangeId` | Camel exchange ID |

**Profile-Specific Logging:**
```yaml
# Test profile - plain text logging for readability
"%test":
  quarkus:
    log:
      level: DEBUG
      json:
        console:
          enable: false                  # Disable JSON in tests

# Integration test profile
"%itest":
  quarkus:
    log:
      level: DEBUG
      json:
        console:
          enable: false
```

**Disabling JSON Logging (Development):**

For local development, you may prefer plain text logs:
```yaml
quarkus:
  log:
    json:
      console:
        enable: false
```

Or via environment variable:
```bash
./mvnw quarkus:dev -Dquarkus.log.json.console.enable=false
```

**Log Output Destinations:**

| Destination | Configuration |
|-------------|---------------|
| Console | Enabled by default |
| File | `quarkus.log.file.enable=true` |
| Syslog | `quarkus.log.syslog.enable=true` |

> **Tip:** For production deployments with ELK/Splunk/CloudWatch, keep JSON logging enabled. The `@timestamp` field and flat MDC fields are compatible with most log aggregation systems.

```xml
  <profile>
    <id>quality</id>
    <build>
      <plugins>
        
        <!-- Override Checkstyle config -->
        <plugin>
          <groupId>org.apache.maven.plugins</groupId>
          <artifactId>maven-checkstyle-plugin</artifactId>
          <configuration>
            <configLocation>${project.basedir}/config/checkstyle/checkstyle.xml</configLocation>
          </configuration>
        </plugin>

        <!-- Override SpotBugs exclusions -->
        <plugin>
          <groupId>com.github.spotbugs</groupId>
          <artifactId>spotbugs-maven-plugin</artifactId>
          <configuration>
            <excludeFilterFile>${project.basedir}/config/spotbugs/exclude.xml</excludeFilterFile>
          </configuration>
        </plugin>

        <!-- Override PMD rules -->
        <plugin>
          <groupId>org.apache.maven.plugins</groupId>
          <artifactId>maven-pmd-plugin</artifactId>
          <configuration>
            <rulesets>
              <ruleset>${project.basedir}/config/pmd/ruleset.xml</ruleset>
            </rulesets>
          </configuration>
        </plugin>

      </plugins>
    </build>
  </profile>
</profiles>
```

> **Note:** The formatter plugin override goes in the main `<build>` section (runs during `validate` phase), while Checkstyle, PMD, and SpotBugs overrides go inside the `quality` profile.

> **Tip:** You can export formatter settings from your IDE:
> - **Eclipse:** Preferences → Java → Code Style → Formatter → Export
> - **IntelliJ:** Settings → Editor → Code Style → Java → Export (select "Eclipse XML Profile")

**Suppressing Rules Inline:**

You can also suppress specific rules directly in your code using annotations or comments:

| Tool | Suppression Method |
|------|-------------------|
| Formatter | `// @formatter:off` ... `// @formatter:on` |
| Checkstyle | `@SuppressWarnings("checkstyle:MagicNumber")` |
| SpotBugs | `@SuppressFBWarnings("NP_NULL_ON_SOME_PATH")` |
| PMD | `@SuppressWarnings("PMD.UnusedLocalVariable")` |

## Deployment

### Docker

The project includes Docker support with multiple Dockerfile options:

**Available Dockerfiles** (`src/main/docker/`):

| Dockerfile | Description |
|------------|-------------|
| `Dockerfile.jvm` | Standard JVM-based image (default) |
| `Dockerfile.legacy-jar` | Legacy JAR packaging |
| `Dockerfile.native` | Native executable image |
| `Dockerfile.native-micro` | Minimal native image |

**Build and Run:**
```bash
# Build the application JAR first
./mvnw package -DskipTests

# Build and run with Docker Compose (includes all backend services)
docker compose up --build -d

# View logs
docker compose logs -f quarkus-rest-proto

# Stop all services
docker compose down
```

**Docker Compose Configuration:**

The root `docker-compose.yaml` automatically includes all backend services and is configured to use the JVM Dockerfile by default:
```yaml
# Backend services are automatically included
include:
  - path: src/integration-test/resources/compose-backends.yml

services:
  quarkus-rest-proto:
    build:
      context: .
      dockerfile: src/main/docker/Dockerfile.jvm
    image: camelbee/quarkus-rest-proto
```

This means running `docker compose up` will start both the microservice and all its dependencies (databases, message brokers, mock servers, etc.).

To use a **native image** instead, use `docker-compose-native.yml`:
```yaml
services:
  quarkus-rest-proto:
    build:
      context: .
      dockerfile: src/main/docker/Dockerfile.native
    image: camelbee/quarkus-rest-proto
```

> **Note:** Before using the native Dockerfile, you must first build the native executable:
> ```bash
> ./mvnw package -Dnative -Dquarkus.native.container-build=true -DskipTests
> ```

### Native Container
```bash
# Build native executable in container (no GraalVM required)
./mvnw package -Dnative -Dquarkus.native.container-build=true -DskipTests

# Build native container image
docker build -f src/main/docker/Dockerfile.native -t quarkus-rest-proto:native .

# Or use Docker Compose Native
docker compose -f docker-compose-native.yml up --build -d
```
